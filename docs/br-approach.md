# Blast Radius: 문제와 풀이 방향

## 문제

sqlglot(파이썬 SQL 파서)에 대한 patch가 커밋마다 하나씩 주어진다. 각 커밋에 대해 돌릴 테스트를 고르고 최대 8개 worker에 나눠서 JSON 한 줄로 출력한다.

점수(낮을수록 좋음):

    커밋 비용 = 가장 바쁜 worker의 테스트 시간 합 + worker당 2초 (아무것도 안 돌리면 0)
    + 실패하는 테스트를 하나라도 빠뜨리면 300초
    + 우리 프로그램이 쓴 CPU 시간 전체

- 테스트 1620개, 기록된 시간 합 103초. 제일 긴 것: `test_max_nodes` 28.8초, `test_execute_tpcds` 21.5초, `test_generator_memory` 6.7초.
- baseline(전부 3 worker로) 1614초, 커밋 40개 정도. 현재 1등 126초.
- sample 30개에 정답을 대입하면 94.4초. 이게 sample에서 낼 수 있는 하한이다. 1등이 커밋당 3초 안팎이니 상위권은 사실상 정답을 맞히고 있다.
- sample 30개 중 13개는 깨지는 테스트가 없다(정답은 `[]`, 비용 0). 나머지 17개도 대부분 1~2개만 깨진다.

## 무엇이 점수를 결정하나

1. **miss 0개.** miss 하나가 300초라서 1등 점수 전체의 두 배가 넘는다. 애매하면 무조건 넣는다.
2. **아무것도 안 깨지는 커밋에 `[]`를 내는 것.** 커밋 절반 가까이가 여기에 해당하고, 하나라도 넣으면 최소 2초에 테스트 시간이 붙는다.
3. **비싼 테스트를 함부로 넣지 않는 것.** tpcds 하나만 넣어도 21.5초다. 정답 하한 94초 중 50초가 tpcds가 실제로 깨지는 커밋 두 개에서 나온다.
4. **CPU 시간.** 컨테이너 안에서 테스트를 직접 돌려 보는 건 허용되지만 그 CPU가 점수에 더해진다.

## 풀이: 정적 후보 + 싸게 돌려서 확인

두 단계로 간다.

**1단계, 후보 고르기 (정적).** 고정된 sqlglot 커밋에서 테스트마다 실행한 줄을 미리 기록해 둔 coverage 맵(`maps/map.json`)을 쓴다.

- patch가 바꾼 파이썬 파일의 AST가 원본과 같으면(주석, 빈 줄만 바뀐 경우) 영향 없음.
- 바뀐 줄이 모두 함수 안이면, 그 함수를 실행한 테스트만 후보.
- 클래스나 모듈 수준(딕셔너리 테이블, 새 메서드 추가 등)이 바뀌면 지금은 전체를 후보로 둔다. 이 부분은 더 좁힐 예정.
- fixture 파일(`tests/fixtures/...`)은 그 파일을 연 테스트가 후보.
- 그 밖에 모르는 종류(설정 파일, 새 파일, 이름 변경 등)는 전부 후보.

**2단계, 확인 (동적).** 후보 중 짧은 테스트는 컨테이너 안에서 patch를 적용한 sqlglot에 대고 실제로 돌려 본다. 통과한 건 빼고 실패한 것만 남긴다. 긴 테스트는 돌리는 비용이 넣는 비용과 비슷하거나 더 커서 그냥 넣는다. 커밋마다 "돌려서 줄이는 비용"과 "그냥 다 넣는 비용"을 비교해서 싼 쪽을 고른다.

이렇게 하면 처음 보는 종류의 변경(파이널에 "practice에 없던 종류"가 나온다고 했다)이 와도 정적 규칙이 놓친 부분을 실제 실행이 잡아 준다.

## 구현 메모

- `/tmp`는 64MB라서 sqlglot을 복사하지 않고 심볼릭 링크로 미러링한 뒤 바뀐 파일만 실제로 쓴다 (`runner/overlay.py`).
- patch 적용은 파이썬으로 직접 한다 (`runner/patchapply.py`). 이미지에 `patch`나 `git`이 없고, 빌드 때 apt로 받는 건 규칙상 애매해서 피했다. sample 30개 전부 `git apply`와 결과가 같다.
- 테스트 실행은 fork 방식이다 (`runner/verify.py`). 부모가 pytest, pandas, duckdb를 한 번만 import하고 커밋마다 자식을 fork한다. 자식은 patch된 트리에서 sqlglot을 새로 import한다.
- 결과는 파이프로 한 줄씩 받는다. 시간 안에 안 끝나면 자식을 죽이고, 끝나지 않은 테스트는 전부 넣는다.

## v3: 싼 후보로 긴 테스트를 대신 판단

서버 점수 266 s를 보고 바꾼 부분이다.

- 후보에 긴 테스트(1.5 s 초과)가 있으면 같은 줄을 지나는 짧은 후보를 먼저 돌린다.
- 짧은 후보가 3개 이상이고 하나도 안 깨지면 긴 테스트도 뺀다. 같은 코드를 지나는 테스트가 여럿 통과했으니 긴 테스트도 통과한다고 보는 것이다.
- 하나라도 깨지면 그 자리에서 멈추고 긴 테스트와 남은 짧은 후보를 전부 넣는다.

이건 추측이 들어간 판단이라 miss 위험이 있다. 긴 테스트만 잡아내는 변경이 오면 300 s를 문다. 그래서 검증 커밋 120개에서 "짧은 후보는 다 통과했는데 긴 테스트가 깨진" 경우가 몇 번인지 세고 나서 제출한다.

sample: 시뮬레이션 158.9 → 108.7 s, 확인 CPU 약 15 s, miss 0.
